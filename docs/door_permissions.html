door の権限 — なぜ止まり、どう直すか

2026-09-20総合受付 (sougou)実測あり

foyer の door が permission denied を返す話。 --mode full は答えではなく、allowlist が無いことの対症療法だった、という一本の筋で説明します。

先に結論

1. allowlist は OS の権限付与ではない。Claude Code が OS の上に持つ「関所」への事前回答で、full mode より狭い。

2. door は非対話なので、許可を聞く相手がいない。事前回答が無いと全部拒否される。

3. その事前回答は 書く場所を間違えると黙って効かない。committed の settings.json は「フォルダの信頼」を待つ。

1. 関所はどこにあるか

最初につまずくのはここです。OS の権限（chmod の世界）とは別の層の話をしています。 root で動いていれば OS レベルでは最初から何でもできる。allowlist はそこには触れません。

つまり allowlist は「できることを増やす」のではなく、聞く手間を省いているだけです。 対話セッションなら人間が都度 Yes と答えて同じことが起きる —— それを先に書いておくのが allowlist。

2. 3 つのモード

door が動く／動かないは、この 3 パターンのどれかです。2 が今までの状態、3 が直したあとの状態。

設定意味広さ
--mode full関所ごと撤去。何を要求されても通す広い
allowlist関所は残す。挙げた操作だけ素通り狭い

--mode full は claude --dangerously-skip-permissions で起動します。 root ではこのフラグが拒否されるので、コンテナや CI では full mode の door はそもそも立ち上がりません。

3. 書く場所を間違えると、黙って効かない

ここが一番ハマった所です。allowlist を書いても効かず、記法を疑って時間を溶かしました。 原因は記法ではなく場所でした。

permissions.allow は「フォルダの信頼」を待つ。 commit した .claude/settings.json に書いても、trust dialog に Yes と答えるまで効きません。 door は非対話なので、その dialog に答えられない。

切り分けを難しくしたのは、hooks は信頼を待たずに動くことです。 同じ settings.json の中で hook だけが効き、allow だけが効かない。 「設定ファイルは読まれているのに allow が無視される」という、原因の見えない症状になります。 （deny と ask も即座に効きます。待つのは allow だけ。）

settings.local.json の allow が待たないのは「repo のものでなく個人のもの」だからです。 裏を返すと git 管理下に入った瞬間、commit したファイルと同じ扱いになる。 .gitignore に入れるのは作法ではなく、動作条件です。

4. 記法の落とし穴

Write(path) というパス規則は一致しません。 Write / Edit / NotebookEdit すべて Edit(path) で書きます。 Write(records/**) と書いても、エラーにはならず黙って効きません。

いま llm-wiki に入っている中身:

{
  "permissions": {
    "allow": [
      "Bash(./scripts/wiki *)",
      "Bash(scripts/wiki *)",
      "Bash(rg *)",
      "Edit(entities/**)",
      "Edit(records/**)"
    ]
  }
}

司書が実際に使うのは scripts/wiki の 9 動詞と、ID 検索の rg だけ。 書き込みは entities/ と records/ の 2 つに限っています。 scripts/ や .claude/ への書き込みは通りません。

5. 効いているかの確かめ方

door 本人に 1 回聞けば分かります。

foyer ask llm-wiki "./scripts/wiki find test を実行して結果を 2 行で"

通っている permission denied が出ず、結果が返る。

効いていない ⚠ permission denied: Bash が出る。→ 書いた場所を疑う（図3）。

hook が動いているかを見たいとき

llm-wiki の SessionStart hook は [llm-wiki] entities: … で始まる 6 行を context に注入します。 door に「その注入が届いているか」を聞けば、設定ファイルが読まれているか自体が判定できます。 今回の切り分けはこれが決め手でした。

6. 今回の経緯

起きたこと分かったこと
llm-wiki の door が起動しないfull mode = --dangerously-skip-permissions。root では拒否される
なぜ full が要るのか調べたsettings.json に hooks しか無く、allowlist が 0 件だった
settings.json に allowlist を追加 → 効かないcommitted の allow は「フォルダの信頼」を待つ
hook は届いていた設定ファイルは読まれている＝記法ではなく場所の問題
settings.local.json に移した解決 door は safe のまま司書がフルに動く

結果として --mode full は不要になりました。 full mode は「許可が広い」のではなく「関所が無い」。 allowlist への置き換えは、許可を広げる変更ではなく絞る変更です。
