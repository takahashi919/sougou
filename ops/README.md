# ops — 分担の管理と配布

複数の作業場（リポジトリ・セッション・AI）にまたがる仕事を、誰が次に動くかで回す仕組み。
状態の正本は各リポジトリの git に置き、ここには「どこを見るか」と「決まり」だけを置く。

## 層

| 層 | 担当 | やること | やらないこと |
|---|---|---|---|
| 判断 | オーナー | 承認・GO・公開・取り込み・削除 | — |
| 管理 | Claude（クラウド） | 引継ぎを書く、受け手を決める、配布を依頼する、結果を git で確かめる | 作業そのもの |
| 配布 | Muse | 依頼された宛先に、決まった1文を届ける。届いたかを記録する | 判断、文の書き足し・要約、質問への回答、承認の言葉を運ぶこと |
| 作業 | Claude / Codex / 調査役の Muse | 引継ぎを読んで作業し、結果と引継ぎを同じブランチに残す | — |

配布役と調査役は、同じ Muse でも別の役として扱う（別のサイドチャットで動かす）。

## 正本の置き場

| もの | 場所 |
|---|---|
| 案件ごとの状態 | 各案件ブランチ直下の `HANDOFF.md`（書式は `handoff-format.md`） |
| エピソードの工程状態 | Research の `episodes/<id>/production.json` |
| 進行中の案件の一覧 | `ops/cases.md`（どこを見るかだけ。状態は書かない） |
| 配布の依頼 | `ops/dispatch/queue.jsonl`（管理役だけが追記する） |
| 配布の記録 | `ops/dispatch/log.jsonl`（配布役だけが追記する） |

進捗の一覧は保存しない。表示する側が毎回 git から作る。

## 決まり

1. 作業役は、作業を終えたとき（途中で止めるときも）コミットして GitHub に push し、同じブランチの `HANDOFF.md` を更新する。push していない作業は、管理役からも進捗表示からも見えない
2. 管理役は、配る前に「`HANDOFF.md` の最終更新」と「ブランチ先端のコミット」の日付を比べる。引継ぎが古ければ配らず、先に直させる
3. 管理役の指示文には、目的・やらないこと・完了の定義・報告の形（根拠つき、不明は不明）を入れる
4. 管理役は報告をそのまま信じず、コミット・受領証・数値で確かめてから「済」にする
5. 承認・GO・公開・取り込み・削除の言葉は、配布の経路に乗せない。オーナー本人が言う
6. 配布のきっかけは `queue.jsonl` の依頼だけ。オーナーの会話や作業役の返事をきっかけにしない
7. 書き込み（commit・push）を伴う依頼は、受け手のセッションでオーナー本人の一言 OK を得てから動く。読むだけの依頼は連絡だけでよい（2026-11-17 リヴィアタン回で確認。受け手は別セッションの「了承済み」を承認と扱わず、本人に確かめた）。受け手が画面を持たない形（SSH 経由の `codex exec` など）で動く場合は、オーナーの指示を `log.jsonl` の `note` に残すことで代える

## 配布の経路

| 宛先 | 経路 | 状態 |
|---|---|---|
| クラウドの Claude セッション | 管理役がセッション間の連絡で直接送る | 2026-11-17 試験済み（往復約20秒） |
| ローカルの door（paleo-video、llm-wiki） | Muse が Tailscale 経由で配布用スクリプトを実行（中で `foyer ask`） | 未開通。Tailscale のトンネルが切れる問題が先 |
| Codex | ローカル PC 上の実行ファイル経由 | 未整備 |

ブラウザで claude.ai に文字を打ち込む配布はしない（オーナー本人の発言として届くため）。

## 配布の1文（固定）

```
Read HANDOFF.md on branch <branch> of <repo>, then continue from its next step. Commit and push your results and the updated HANDOFF.md to the same branch.
```

ローカル側ではこの文を配布用スクリプトの中に固定し、Muse が渡せるのは door・repo・branch の3つだけにする。

- **文は ASCII だけで書く。**2026-11-18 の初回配布で、PowerShell のパイプを通った日本語が「????」に化け、Codex は作業を始めなかった。引継ぎ本体は UTF-8 のファイルとして読まれるので、日本語のままでよい
- 配布用スクリプトは、引数（door・repo・branch）に ASCII 以外の文字があれば送らずに止まる
- 受け手の最初の返事に「?」の連続があれば、`result` は `failed` として記録し、再送はしない（オーナーに知らせる）

## 依頼と記録の書式（1行1件の JSON）

`queue.jsonl`（管理役が追記）:

```json
{"id":"2026-11-18-01","route":"foyer","door":"paleo-video","repo":"takahashi919/paleo-video","branch":"claude/example","requested_at":"2026-11-18T09:00:00+09:00"}
```

`log.jsonl`（配布役が追記）:

```json
{"id":"2026-11-18-01","sent_at":"2026-11-18T09:12:00+09:00","result":"delivered","exit":0,"note":""}
```

- `result` は `delivered` / `busy`（終了コード3。あとで1回だけ再送）/ `failed`
- `log.jsonl` に同じ `id` があれば処理済み。2回送っても `busy` なら3回目は送らずオーナーに知らせる
- 文面そのものは記録に複写しない（スクリプトが正本）

## 進捗の表示（Muse のスペース）

`cases.md` の各行について、30分ごとに次を作って表示する。手入力はしない。

| 列 | 出どころ |
|---|---|
| 件名 | `HANDOFF.md` の `title` |
| 受け手 / 次に動く | `to` / `next` |
| 判断待ち | `waiting` |
| 引継ぎの更新日 | `HANDOFF.md` を最後に変えたコミットの日付 |
| 最新コミット | ブランチ先端のコミットの日付 |
| 要確認 | 最新コミットが引継ぎより新しい（目安であって保証ではない） |
| 直近の配布 | `log.jsonl` の最新行。配布後24時間、そのブランチに新しいコミットが無ければ「未着手」 |
| 読み取り | 冒頭ブロックが読めなければ「読み取り失敗」と出す（推測で埋めない） |

「未着手」と「読み取り失敗」はオーナーに知らせる。
